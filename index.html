    SimoAI

    SimoAI

    I wanted my own AI assistant before the end of the year, and I started with no AI knowledge at all. Three weeks later it was a local app where one model plans, specialist models do the work, and the interface only reports what actually ran.

    Runs on my PC, not online

    When
    25 Sep – 12 Oct 2026
    My part
    Product owner and tester. The routing idea, every feature choice, every bug report.
    Code
    Written by Codex, an AI coding agent
    Hardware
    Intel i5-14500, 32 GB RAM, RTX 5060 Ti with 16 GB
    Stack
    Node.js, Ollama, ComfyUI, IndexedDB

    How it started

    I had two ideas: a personal chatbot, and a site called BuildAI that would teach beginners to make one. I built the chatbot first, so that any course later would come from a real beginner’s journey. I also dropped “train my own ChatGPT” early. The realistic goal was an app on top of existing open models.

    We split the work on day one. I chose the features, tested them, reported what failed and learned at my own pace; the agent wrote the code and explained it. Nearly every feature below exists because I tried something and it broke.

    What it does

    • Chat with Qwen3 14B through Ollama, entirely on the PC.
    • Auto mode: Qwen3 14B plans up to six tasks across chat, code, vision, images, video, diagrams and motion graphics, and hands each one to a specialist.
    • Code with Qwen3-Coder 30B, split between the graphics card and system RAM.
    • Vision with Gemma 3 12B for attached images.
    • PDFs: selectable text up to 50 pages or 50,000 characters, and the first five pages rendered for the vision model when a PDF is scanned.
    • Images with Qwen-Image 2.1 and FLUX.1 Schnell, and video with Wan 2.2 (from text or from an image), all through ComfyUI.
    • History in IndexedDB. Each conversation keeps its own model and settings and can be searched, renamed or exported as Markdown.
    • One-click start from a desktop shortcut, and a Quit button that only stops the processes SimoAI itself started.

    How a request runs

    1. Browser
    2. Node.js server
    3. Qwen3 14B plans the tasks
    4. Orchestrator and GPU queue
    5. Ollama, ComfyUI or the exact renderer
    6. Each result streams back

    The GPU queue matters most. A 16 GB card can’t hold a 30B coder, an image model and a video model at once, so jobs run one at a time and idle image models are released before text work. Each result appears the moment it’s ready, so a slow video never holds up the written answer. Play with the queue as a machine in “How I work”.

    Made on my GPU

    The kitten was generated by Qwen-Image 2.1 through SimoAI, then animated by Wan 2.2. Nothing was sent to a cloud service. The video model is still the weakest part: a finished MP4 proves the pipeline ran, not that the motion looks good.

    Three bugs that shaped it

    The circle request
    I asked Auto mode to explain the area of a circle, draw a blue circle with the formula and animate a dot growing into a circle. I got an unrelated office scene and lost the written answer. Fix: requests are split into explicit tasks, the text answer comes first, and exact geometry goes to a precise renderer instead of an image model. The same request then finished in 48 seconds with all three outputs.
    The 40-minute video
    One “quality” run spent about 33 minutes inside Wan rendering 121 frames at 1280×1216. Fix: a budget of 25.6 million pixel-frames, roughly two-second defaults and GPU text encoding with offload. A controlled 49-frame test dropped from about 3 min 20 s to 2 min 22 s.
    The save that “passed”
    A generated image failed to save with a Windows permission error. The first fix passed a mocked test and then failed a real one. Fix: ComfyUI’s input, temp and output folders moved inside the project, with read-only access kept for older images. Checked with a real generation through SimoAI’s own API; 19 of 19 tests passed.

    Measured, not assumed

    In a head-to-head on a parser task, a free cloud chatbot clearly beat SimoAI. Instead of deciding “local models are bad”, we built a small benchmark: eight JavaScript tasks with hidden test groups, one attempt each, temperature 0, fixed seed.

    52 of 65 hidden test groups, 4 of 8 tasks fully passed.

    It was strong on an LRU cache, interval merging, dependency sorting and safe nested lookup, and weak on command parsing, a CSV edge case, debounce and deep equality. It’s a small local test, not a leaderboard. Good for routine code; parsers still need tests.

    Limits

    • LTX-2.5 video is wired into the app, but its gated weights were never installed, so the interface says it’s unavailable instead of pretending.
    • An 80B coding model didn’t fit: it needed about 38 GiB of system RAM on a PC with 31.7. I removed it and wrote down why.
    • I never weakened Windows security or pasted secrets anywhere to make something run, even when that was the shortcut.

    What I learned

    A useful assistant is a system, not one giant model: an interface, model runners, file handling, status checks, safe credentials, routing, media storage and tests. A router model can coordinate all of it, but only if it keeps every deliverable the user asked for.

    And evidence has to match the claim. A menu entry isn’t a download, a download isn’t a working model, and a working model isn’t a good result.

    Next: Ironline, browser tactical shooter
    Ironline

    Ironline

    How close can a browser get to a competitive tactical shooter? Ironline is an original 5v5 plant-and-defuse game with abilities, an economy and bots that trade, lurk and save. Every name, model and sound in it is original.

    Runs locally, not deployed

    When
    Sep – Oct 2026
    My part
    Game design, scope, and deciding when something was good enough
    Code
    Written by Claude Code, an AI coding agent
    Tests
    290 passing in 27 files (run on 14 Oct 2026)
    Stack
    TypeScript, Vite, Three.js, Web Audio, WebSockets, Vitest

    Where it came from

    My first attempt, Vector Strike, had one map, four weapons and bots. It was fun, and it showed exactly what was missing: the rules lived inside the rendering code, the bots were easy to read, and nothing could be tested without playing. Ironline started from those three lessons, plus one rule: inspired by the genre, but every asset and name original.

    How it’s built

    1. Input
    2. Simulation: 128 ticks a second, deterministic
    3. Renderer, HUD and sound only read it

    The game rules know nothing about graphics. The simulation is a pure, deterministic step at 128 ticks per second; bots and the network write to it, and rendering, sound and the HUD only read it. That makes rounds reproducible, lets bots be balanced by simulating rounds with no screen at all, and keeps multiplayer simple, because the host runs the same simulation everyone sees.

    What’s in it

    • 3 maps (Foundry, Terminal, Skybridge), 5 agents with four abilities each, 9 weapons and a blade.
    • A full 13-round match with side swap and overtime, a credit economy, and buy, plant and defuse phases.
    • Bots from Easy to Elite that trade kills, lurk and save, and a practice range with drills and live accuracy stats.
    • Fixed recoil patterns, movement inaccuracy, wall penetration, killcam, rebindable keys and career stats.
    • All audio generated in code: a sound per weapon, positional audio, muffling through walls, reverb and a menu loop.
    • LAN multiplayer through a WebSocket server with no dependencies.

    Limits

    • Multiplayer has no client prediction or lag compensation. Fine on a LAN, not ready for the internet.
    • The feel (mouse, recoil, sound) was tuned more by numbers than by long playtesting.
    • The only downloaded art is a few public-domain surface textures. Everything else is generated, and it shows up close.

    What I learned

    Separating what is true (the simulation) from what you see (the rendering) is what makes a complicated real-time system testable. Without it, the only way to find a bug is to play until it happens.

    Next: ArchaeoSmart, offline field app
    ArchaeoSmart

    ArchaeoSmart

    Archaeologists in the field still write their finds on paper: fragile, unstructured, impossible to search. Our FLL innovation project was a phone app that records finds properly and keeps working with no signal.

    Open the app (opens in a new tab)Code on GitHub (opens in a new tab)

    When
    The 2025–26 FLL season
    Team
    LOGIKO. I was the oldest and the only one with competition experience; everyone else was new.
    Result
    1st place in Morocco, and a place at the international championship in Houston
    Code
    Me, starting from zero web experience
    Stack
    HTML, CSS, JavaScript, PWA, Leaflet, Web Speech API, QRCode.js, Canvas

    What it does

    A mobile-first web app you can install: voice-guided recording of each find, GPS tags, QR labels you can print and scan, a canvas for site sketches, a map, statistics and CSV export. There is no server. Everything happens on the phone, so it works offline.

    How it works

    Input
    Spoken answers, form fields, GPS position, QR scans and sketches
    Storage
    Each record is saved on the device, so the app keeps working without internet
    Finding things again
    QR codes and searchable IDs connect a physical find to its record

    The constraint that shaped everything was reliability in the field. The app had to keep collecting data when the network disappeared, so offline was the core of the design, not an extra.

    The hardest part

    The voice interview, where the app asks questions and you answer out loud. Getting the Web Speech API to behave the same on iOS and Android took weeks. Safari handles microphone permissions differently from Chrome, and stopping continuous recognition from cutting people off mid-answer took a lot of attempts. It works now.

    What I’d fix

    Records live in the browser’s storage and disappear if it’s cleared. A real version needs a sync queue, a remote database, accounts, and a way to merge two people editing the same find offline. I’d start with an event log and only reach for CRDT-style merging if collaboration became central.

    What I learned

    Building something that has to work in a field teaches you things you’d never look up on your own. I had no web experience when the season started, and neither did my teammates.

    Workspace OS

    Everything I’d built before had no database, no accounts and no server. I knew that gap would hold me back, so I built an app just to close it.

    Open the app (opens in a new tab)Code on GitHub (opens in a new tab)

    When
    2026, built in one day
    Why
    Deliberate practice: learn how backends really work
    Code
    Me
    Stack
    Supabase, PostgreSQL, row-level security, JavaScript

    What it does

    Email and password accounts, workspaces you can create and delete, two roles (owner and member), invite codes, projects, tasks with priorities, and an audit log of who did what.

    How the data works

    Things
    Users, workspaces, memberships, projects, tasks, audit logs
    Links
    A user can join many workspaces; workspaces own projects; projects own tasks
    The rule
    Nobody reads or changes anything outside the workspaces they belong to

    Supabase handles sign-in and the PostgreSQL database. Row-level security enforces the rule inside the database, not only in the interface, so even if someone skips the front end the database still says no.

    What I learned

    The hard part wasn’t the code. It was thinking in relationships: who owns what, and how do you stop a member from deleting an owner’s project? Those are design questions before they’re coding questions.

    Trade-offs and next

    Supabase let me learn accounts, relational data and row-level security fast, but it ties the project to its way of writing rules. Next I’d add live collaboration, email invites, pagination for big workspaces, and server-side functions for actions that shouldn’t run in the browser.

    Next: PoseSandbox, 3d posing tool
    PoseSandbox

    PoseSandbox

    Artists need quick 3D pose references, and most tools are expensive desktop software or clumsy web ports. I wanted one that opens instantly, needs no account and exports an image without fuss.

    Open PoseSandbox (opens in a new tab)Code on GitHub (opens in a new tab)

    When
    2024–25, my first website
    Code
    Me
    Stack
    Three.js, WebGL, transform controls, JSON save files

    How it works

    Interface
    Tool buttons, modes, save and load, reference image, export
    Interaction
    Mouse input turned into 3D intent with raycasting, selection and transform controls
    Rendering
    The Three.js scene, camera, lights, body parts, props and redraw loop
    1. Click
    2. Raycast
    3. Select a joint
    4. Transform
    5. Render
    6. Export or save

    Showing a 3D model was the easy part. The real problem was turning a 2D click or drag into a predictable 3D move, while keeping the camera, joint selection and transforms from fighting each other. Keys 1 to 4 switch between rotate, move, orbit and scale.

    Why Three.js

    Raw WebGL would have meant spending the whole project on shaders and buffers. Three.js gave me a scene graph, camera controls, lights and loaders, so I could work on the harder problem: making 3D posing understandable to people who aren’t technical.

    Trade-offs

    It uses a hand-built joint hierarchy instead of a full skeletal rig. That made it buildable as a first 3D app, but rotations can feel mechanical, and complex poses take more work than inverse kinematics would.

    What I’d change

    A real rig with inverse kinematics, undo and redo through state snapshots, cleaner separation between rendering and interface code, and limits that keep heavy scenes fast. The biggest lesson: interactive tools are mostly state problems, and confusing state makes a confusing tool.

    Open differential

    Next: Evenly, expense splitter
    Evenly

    Evenly

    Split a group’s costs, then settle up in as few payments as possible.

    A single offline file

    When
    September 2026
    Code
    Written by Codex, an AI coding agent
    Stack
    Vanilla JavaScript, works offline

    Money

    Amounts are stored in whole cents. When a bill doesn’t divide evenly, the leftover cents are handed out by largest remainder, so the shares always add up to the total.

    Settling up

    Finding the true minimum number of payments is NP-hard, so Evenly pairs people whose amounts match exactly first, then matches the largest debt with the largest credit until everyone is even.
